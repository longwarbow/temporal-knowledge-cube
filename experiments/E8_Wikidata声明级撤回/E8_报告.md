## 0 一句话结论

Wikidata 里 **10,970,321 条声明被 `rank=deprecated` 标记撤回**（全库实测量），
撤回率谱系 **0.0113%–0.1226%（9 属性精确值）** / **≥0.0088%–≥0.1892%（7 大属性下界）**、原因 292 种、并自带**声明级 (s,r,o) + 时刻代理**结构 ——
它把 RQ1 §4 的「`active → retracted` 状态迁移」从**设计里的状态**变成了**有 1100 万条真实标注的状态**。
**`deprecated` 不删除旧值**，与我们的 `retracted/superseded` 语义完全同构 ⇒ 论文里可写成
「同一问题在知识图谱工程中已被工程化 20 年」（与 CTAmap 之于地理维同理）。

## 2 方法与通道（含两个必须写进论文/方法论的坑）

### 2.1 通道
- 端点 `https://query.wikidata.org/sparql`（WDQS）。
- **坑 A（本机环境，两条独立的网络问题，二者同时存在）**：
  （i）运行环境**注入了本地代理**（`https_proxy=http://127.0.0.1:41665`），该代理**拦 Wikimedia 域**
  （CONNECT 隧道能建、随后 TLS 被断 ⇒ `HTTP 000`/`curl exit 35`），但放行其他域（如镜像站）
  ⇒ **所有 Wikimedia 请求必须 `--noproxy '*'` 直连**；症状是「时而通、时而全挂」，不加此参数极难排查；
  （ii）本机 Python 的 TLS 栈（OpenSSL）请求**被中止**（`WinError 10053`），而 `curl`（schannel）可通
  ⇒ 统一「Python 编排 + curl 子进程执行」。
  与 RQ3 的可复现性声明有关：**脚本已固化该通道**（`--noproxy '*'` + curl 子进程），不依赖 Python TLS。

### 2.2 查询计划规律（★ 本实验最重要的技术发现）
| 查询形状 | 代价 | 实测 |
|---|---|---|
| 纯 rank 索引锚定：`?st wikibase:rank wikibase:DeprecatedRank` | 单索引扫描 | **0.46 s** 返回全库计数 |
| `?item p:P569 ?st`（total 计数） | 属性索引扫描（8.4M） | ✅ 秒级 |
| `?item p:Pxxx ?st . ?st rank DeprecatedRank` | rank 访问 = **逐声明一次 statement-node 随机读** | ❌ 大属性必 `504 upstream request timeout` |
| reason 锚定：`… ; pq:P2241 ?reason` | 限定符索引先行 | ✅ P569 也只要 10–32 s |

⇒ **工程结论**：属性级「精确」撤回计数只对小属性（< ~2–3 M 声明）可行；
大属性退化为「**带原因下界**」（本次 16 属性中 7 个取下界）。
论文中的百分比必须标注 `≥`，不可混用。此规律已写入脚本注释，供复现。

## 3 结果

### 3.1 头条：规模
- **全库 `deprecated` 声明 = 10,970,321 条**（一次 rank 索引扫描，0.46 s）。
- 16 个高发属性合计 42,980,256 条声明，其中 deprecated **32,974 条**
  （9 属性精确值 8,961 + 7 大属性下界 24,013）。
- 含义：**「声明被撤回」不是罕见事件，而是知识图谱日常运维的常规操作**——
  这正是 Q5/late-arriving/状态迁移问题在真实世界长期存在的直接证据。

**精确值（9 属性，deprecated / total）**：

| 属性 | 语义 | total | deprecated | 撤回率 |
|---|---|---|---|---|
| P119 | burial place | 421,835 | 517 | **0.1226%** |
| P127 | owned by | 1,184,113 | 1,292 | 0.1091% |
| P20 | place of death | 1,813,631 | 1,962 | 0.1082% |
| P25 | mother | 782,231 | 744 | 0.0951% |
| P26 | spouse | 963,993 | 826 | 0.0857% |
| P159 | headquarters location | 1,022,461 | 857 | 0.0838% |
| P22 | father | 1,257,428 | 988 | 0.0786% |
| P40 | child | 2,033,789 | 1,575 | 0.0774% |
| P54 | member of sports team | 1,777,632 | 200 | 0.0113% |

**下界值（7 大属性，`deprecated ≥ 带原因数`）**：
P570 death date ≥ 7,763 / 4.10 M（**≥0.1892%**）· P569 birth date ≥ 8,066 / 8.46 M（≥0.0953%）·
P27 citizenship ≥ 3,887（≥0.0600%）· P39 position held ≥ 1,191（≥0.0594%）·
P19 place of birth ≥ 2,444（≥0.0554%）· P69 educated at ≥ 433（≥0.0118%）· P108 employer ≥ 229（≥0.0088%）。

**读法**：撤回率与「**该声明是否可被时间/身份类证据推翻**」强相关 ——
关系类（配偶/父母/子女）、场所类（安葬地/死亡地/总部）最高；
**事件型、易随任命变更的位置类（P39/P108/P54）反而最低**（因为更常用 `P582` 正常结项，而不是降级）——
这与 §3.4 的 P582 覆盖率形成**互证**：**同一失效语义有两条工程路径（rank 降级 vs end-time 结项）**。

| Q25895909 | 1,444 | cannot be confirmed by other sources | 无法通过其他来源证实 |
| Q42727519 | 742 | item/value with less precision and/or accuracy | 精度/准确度较低 |

共 **27,094 条带原因**（占 deprecated 的比例随属性而异，样本中 0.27–1.00）。

**对 RQ1/RQ2 的价值**：原因条目与我们 §4 四类维护操作（INSERT/RETRACT/**REVISE**/DRIFT）直接对应：
- `incorrect value` / `error in source` ⇒ **RETRACT（错误型）**
- `less precision` / `should be deprecated but not deleted` ⇒ **REVISE（精度型，旧值保留）** —— ★ 佐证「不删除」原则
- `anachronism` / `at the specified time … 不存在` ⇒ **DRIFT（时序漂移）** —— ★ 与 E2 跨期正确性同源
- `cannot be confirmed` / `source unreliable` ⇒ **降级为 unverified**（与 PHEME 三值对齐）

### 3.4 裁定时刻代理（G7 的另一半）

**（a）`P582`（end time）= 计划性撤回时刻**

| 属性 | 样本内 P582 覆盖 |
|---|---|
| P108 employer | **25.8%** |
| P39 position held | 25.4% |
| P26 spouse | 13.8% |
| P69 educated at | 13.5% |
| P569/P570（日期类） | **0.0%** |

⇒ **该失效语义天生分两路**：任职/关系类走 `P582` 显式结项，日期类走 rank 降级。
**对 Q5 的意义**：受影响 cell 的「失效时刻」在真实 KB 中有**显式来源**（P582）与**隐式来源**（P813 上界）两种，
这正是我们把状态维做成**双时态**（事件时刻 vs 裁定时刻）的现实依据。

**（b）`P813`（retrieved）= 裁定时刻上界**（`E8_P813年度分布.csv`）

- 7,478 条（reason-anchored 子集）带 retrieved 日期；
- **93.6% ≥ 2017**（<2017 仅 6.4%），2017 年出现尖峰 1,216 条 —— 与 Wikidata 的**批量核查/清理活动**同期；
- 读法：retrieved 是「**源被核查**」的时刻，必然 **≥ 该声明被判定为错**的时刻 ⇒ **裁定时刻的上界**；
  用它可以把 Q5 的失效窗口从「不知何时」收紧为「**≤ 某年**」。

### 3.5 声明级样本（G8 的数据基础，`E8_声明级样本.csv`）

- **2,946 条**声明级记录，字段：`(item, pid, value, reason, endtime, retrieved)`；
- 覆盖 P569 / P570 / P26 / P108 / P69 / P39，每属性约 500 条（P69 为 reason 锚定 446 条）；
- **★ 直接证据：跨声明失效传播存在且可量化**（`E8_analyze.py` §6，可复现）——
  在 **500 条 P26（配偶）降级样本**中检出 **94 对互反声明**（`A --P26--> B` 与 `B --P26--> A` 同时降级）：
  其中 **46 对撤回原因完全相同**、**9 对 `end time` 逐位相同**。
  逐位相同的实例（已核验原始行）：
  `Q271865 --P26--> Q189081`（end=1976-04-05，reason=Q25895909 "无法通过其他来源证实"）
  ⇄ `Q189081 --P26--> Q271865`（同 end、同 reason、`retrieved` 同为 2021-01-08）。
  ⇒ 这正是 G8 要验证的「**一条声明失效是否应连带失效关联声明**」的真实实例，
  且**对偶失效是有统计规律的**（互反对中近半数同因、约一成同刻）——可作 TMS 传播实验的种子用例与基线。
- 数据清洁提示（写入样本说明）：`somevalue/novalue` 在 WDQS 中表现为 `genid` URI，须过滤；
  日期值形如 `-0050-01-01T00:00:00Z`（公元前）需按 xsd:dateTime 解析。

## 5 局限与后续

1. **数据是「在线快照」**：WDQS 反映实时库，两次查询间全库计数已从 **10,970,321 → 10,970,325**（+4，间隔约 20 min）。
   论文若引用具体数字，须写明**查询日期 + 端点**，并把脚本作为可复现附件（本组脚本已含 UA 与端点）。
2. **大属性精确计数不可得**（WDQS 60 s 上限 + statement-node 随机读代价）：7 属性为下界，
   论文表格须标 `≥`；补精确值的正路是 **Wikidata dumps 本地解析**（truthy dump ~50 GB+，本机暂不做）。
3. **裁定时刻仍是代理**：`rank` 变更无 RDF 时间戳。
   毫秒/秒级裁定时刻需 **MediaWiki 修订史 API**（`prop=revisions` 逐声明查询，可先做 500–2000 条样本，
   验证「修订时间 — 声明降级」的可抽取性）。**列为下一步小实验（E9 候选）**。
4. **样本仅 6 属性 × ~500**：可扩展到 16 属性全量、并把字段补 `itemLabel`（仅样本级，避免 LabelService 拖垮）。
5. **跨声明传播**：目前已有统计规律（94 对互反 / 46 同因 / 9 同刻）但未做系统实验；需声明图
   （same item / inverse property / depends-on），与 RQ2 的血缘查询共享机制 —— **建议与 RQ2 合并设计**。
