## 2. 适配器形态（`e14_adapter.py`）

```python
PhemeAdapter()                # 加载 + 缓存 gpickle/pkl
  .iter_threads(labeled_only=True)        # 线程级流
  .iter_tweets(labeled_only=True,         # 贴文级流
               min_text_len=1,
               require_source=True,
               include_replies=True)
  .thread_stats(...)                       # 线程级统计
  .tweet_stats(...)                       # 贴文级统计
to_erarag_doc(tweet_dict)                  # {title=snowflake, content=text}
batched(iter, n)                           # 迷你批切
snowflake_to_ms(snowflake_id)              # 毫秒时间轴反解
ms_to_iso(ms)                              # ISO8601 字符串
CedAdapter()                               # 占位：CED 仅作到达流，不进 EraRAG 索引
```

### 关键设计选择

1. **`title = snowflake`**：全局唯一、时间可反解、自带 `text_embedding` 可作为后续独立信号（呼应 E13 轮 9 的"独立信号优先"原则）。
2. **`content = 原始 tweet 文本`**：与 EraRAG 官方期望对齐；可选 `content_prefix_meta=True` 把 `[ISO][label=…]` 拼到文本前，便于检索词命中事件/标签上下文。
3. **时间排序**：调用方在喂入 EraRAG 前按 `ms` 升序排——这模拟"流式到达"语义；adapter 自身不强行排序（保留调用方自由）。
4. **只读 + 惰性加载**：不复制/不写 PHEME 原始文件。
5. **CED 降级为到达流**：转发文本多为空，作为传播时序的副信号而非内容来源。

## 3. 端到端验证（`--mode erarag`，20 贴）

| 指标 | 值 |
|---|---|

## 4. 对论文 RQ3（StreamRumor-Bench）的意义

- **流式输入就位**：W2 提供了"按时间顺序到达"的真实 PHEME 贴文流，可直接喂给 EraRAG 增量插入路径。
- **典型批大小可调**：`batched(iter, 32)` 给出 32 条/批的切法；论文中可声明"每次新增 32 条"作为 baseline 默认。
- **可对比性**：同样 26,207 贴文若全量重建 vs 819 批增量，是观察"增量 vs 全量"成本曲线的天然基准。
- **威胁与限制**：
  - 仅前 200 条样本落在 Ferguson 单一事件区，9 事件的全跨度需要 `max_items` 调大或全量跑。
  - 178 贴/线程的极端大线程会让 LSH 桶失衡——已在 W1 报告过该机制；本数据集最大簇仅 8（20 贴样本），问题未暴露。
  - 雪崩式线程（多线程同一秒到）目前按 ms 平铺，论文应报告"事件内 vs 事件间"的时序粒度选择。
