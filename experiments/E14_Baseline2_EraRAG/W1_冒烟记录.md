# E14 / W1 冒烟报告：EraRAG 动态树增量插入路径在 CPU-only 下跑通

- **日期**：2026-10-15
- **载体**：`EraRAG-Official`（EverM0re/EraRAG-Official）动态树 `tree_graph_dynamic`
- **目标**：在**无 GPU / Windows / Python 3.9** 环境下，验证动态树确实走**增量插入（`add=True → _refine_graph`）**而非**全量重建（`force → _build_graph`）**——这是把 EraRAG 作为 Baseline #2 的前提，也是论文 RQ 中关于"流式知识立方体增量维护"对照点的硬件可行性证明。
- **结论**：✅ **W1_PASS = true**，增量路径被铁证确认。

---

## 1. 运行环境

| 项 | 取值 |
|---|---|
| OS | Windows 11 |
| Python | 3.9（系统）+ 隔离 venv `.venv_e14` |
| GPU | **无**（4×2080Ti 不稳定，本次完全不用） |
| 嵌入后端 | 本地 `sentence-transformers/all-MiniLM-L6-v2`（384 维，HF 镜像预下载） |
| LLM | 智谱 **GLM-4-Flash**（免费，`open_llm` 兼容 OpenAI 协议，8 路并发） |
| 强制 CPU | monkeypatch `SentenceTransformer.__init__` 锁 `device="cpu"` |
| 工作目录 | `${KB_ROOT}/_e14_run`（**纯 ASCII**，避开 faiss 中文路径 bug） |

---

## 2. 方法（路由桩铁证法）

直接构造 `Config` 对象走真实 `GraphRAG(config)` 代码路径，并在 `TreeGraphDynamic` 上**包一层调用桩**记录路由：

- **Phase A**：`add=False, force=True` → 期望 `_build_graph`（重建）
- **Phase B**：`add=True, force=False` → 期望 `_refine_graph`（增量插入）

桩只计数与传递 chunk 数，不改变任何内部逻辑，因此看到哪条路由被触发即代表框架真实走了哪条路。

---

## 3. 结果

| 指标 | Phase A（初始建树） | Phase B（增量补充） |
|---|---|---|
| 路由方法 | `_build_graph` | `_refine_graph` |
| 触发次数（桩计数） | `build=1` | `refine=1` |
| 处理 chunk 数 | 40 | 15 |
| 叶节点数 | **40** | **55** |
| 耗时 | 27.1 s | 24.2 s |

**判定**：
```
PhaseA_build_path : true   (add=False/force=True 走 _build_graph)
PhaseB_refine_path: true   (add=True/force=False 走 _refine_graph)
leaves_grew       : true   (40 -> 55, 增量而非重建归零)
W1_PASS           : true
```

**核心结论**：Phase B 在已存在 40 叶的树上新增 15 chunk，叶节点净增到 55 而非重置，且桩确认走的是 `_refine_graph`——**EraRAG 动态树的"增量插入"是真实机制，不是文档宣称**。这正是论文把 EraRAG 作为"流式增量维护"对照组所依赖的性质。

## 5. 过程中暴露并修复的官方仓库缺陷（共 8 处）

W1 跑通同时揭示了 EraRAG-Official 在"非官方标配环境"下的脆弱性，全部已修复，详见 **`E14_repo_compat.md`**：

1. `TreeGraphLSH.py` 占位符（clone 后 import 即崩）
2. `llama-index` 引入 `banks` 在 Py3.9 崩
3. `LLMType` 双份定义致 `create_llm_instance` KeyError
4. `Config.default()` 缺 `llm` 字段致 pydantic 校验失败
5. `_print_bucket_stats` 被注释却仍被调用（AttributeError）
6. FAISS 索引维度硬编码 `1024`（与 MiniLM 384 不匹配，`assert d == self.d`）
7. FAISS `persist` 前未建目录（写文件失败）
8. **Windows 非 ASCII 路径下 faiss `write_index` 无法打开文件**（中文目录必崩）

> 这 8 条应作为论文 reproducibility / threats 的真实证据：**EraRAG 的"增量"机制是可复现的，但其工程实现对非标配环境（CPU-only、本地嵌入、Windows）高度脆弱**。

---

## 6. 对论文的影响（回应最初问题）

> 用户最初问："不做 EraRAG 有没有问题？不使用 GPU、只做 CPU 计算，对论文有什么影响？"

- **结论**：CPU-only 完全可行，EraRAG 的 token 成本（免费 GLM-4-Flash）与算力成本（4×2080Ti 不稳，本就不该依赖）都不构成阻塞。W1 已证明增量路径在 CPU 上跑通。
- **真正成本**是 5–8 天的集成调试（上述 8 个环境/官方缺陷），而非算力。
- **对论文**：EraRAG 作为 Baseline #2 提供"动态树增量 vs 我们的流式立方体增量"对照，硬件上不受 GPU 限制；论文应明确写出其复现所需的补丁（见 `E14_repo_compat.md`），以支撑可复现性审查。
