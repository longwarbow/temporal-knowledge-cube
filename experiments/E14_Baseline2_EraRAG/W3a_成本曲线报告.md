# E14 / W3a 报告：EraRAG 增量插入成本曲线（PHEME 真实贴文）

- **日期**：2026-10-15
- **目标**：在真实 PHEME 贴文上，量化 EraRAG 动态树的「增量插入」成本，并与「全量重建」对照。
- **结论**：✅ 完成 3 个规模点，揭示 **两个对论文极有价值的负结果**。

---

## 0. 运行说明（工程加固）

v1 版本在 N=200 时**挂死 3.7 小时**（无网络活动、CPU 近 0）——根因是 EraRAG 的
`ThreadPoolExecutor + 每任务新建事件循环` 与主循环创建的 `AsyncOpenAI` 客户端 /
`asyncio.Semaphore` 发生**跨事件循环死锁**（详见 §4 缺陷 #9）。v2 三重加固后全部通过：

1. 每次 LLM 调用外包 `asyncio.wait_for(..., 90s)` 硬超时
2. 用 loop-无关的 no-op 信号量替换 `asyncio.Semaphore`（消除跨 loop future）
3. 进程级看门狗线程（超时 `os._exit`）
4. 单规模独立进程运行

## 3. ★★ 两个重量级负结果

### 负结果 1：EraRAG「增量插入」比「全量重建」**慢 2.4–2.8 倍**

- 补 20% 的新贴，增量路径耗时是全量重建的 **2.4–2.8×**（token 只省 18–25%）。
- **逐新贴耗时随树规模超线性增长**：1.40 → 2.84 → **5.01 s/新贴**（N=50→150→300），翻了 3.6 倍。
- 含义：EraRAG 的 `_refine_graph` 会**重摘要所有受影响内部节点（祖先传播）**，且在线程池里逐任务新建事件循环，导致 **每插入一批的成本随已有树规模增长**——这与「高效增量维护」的预期相反。
- 对照我们的 C3/P1：E1 线已实测「增量 ≡ 全量（0 差异，代价 5.6×）」——**我们的增量保证正确性且代价可预期**；EraRAG 则是「既不省时间、又不保证一致」。

### 负结果 2：EraRAG 增量树结构 ≠ 全量重建树

| N | 增量后内部节点 | 全量重建内部节点 | 差 |
|---|---|---|---|
| 50 | 6 | 8 | **−2** |
| 150 | 21 | 26 | **−5** |
| 300 | 40 | 50 | **−10** |

- 叶节点数一致，但**内部节点数系统性偏少**（增量树更「平」/结构不同），差距随规模扩大。
- 含义：**EraRAG 的增量插入不满足「增量终态 = 全量重建终态」**。这正是我们 P1 增量一致性所主张、并在 E1 线以 0 差异实证的性质。**EraRAG 作为 baseline 在此性质上实测不达标**——是论文中区分「语义版 Stream Cube」与「动态树 RAG」的关键分水岭。

## 4. 新增官方仓库缺陷 #9（可进 Threats）

**EraRAG 的动态树细化路径存在跨事件循环死锁风险**：
- `TreeGraphDynamic._create_task_with_return` 在 **ThreadPoolExecutor 的每个任务里 `asyncio.new_event_loop()`**，而 LLM 的 `AsyncOpenAI` 客户端与 `asyncio.Semaphore` 都是在**主事件循环**里创建的；
- 主线程随后被 `task.result()` **阻塞**，无法驱动主循环；worker 侧一旦需要等待绑定主循环的信号量/future ⇒ 死锁（本机实测挂死 3.7 h，CPU 近乎为 0、无网络活动）。
- Py3.9 下 `asyncio.Semaphore` 绑定创建时的 loop，放大了该问题。
- 缓解：我们的加固（per-call 超时 + no-op 信号量 + 看门狗）可绕过；但**上游代码在小树可跑、随规模增长随时可能挂死**，属可复现性风险。

## 5. 对论文的意义

1. **Baseline #2 的定位清晰**：EraRAG 在「增量维护」这一维度上，**时间不省、结构不一致**。我们的「语义版 Stream Cube」以 P1（增量一致性）+ P2（失效最小重算）为卖点，此处获得**对抗性实证**。
2. **成本曲线可进 §7.7 表 #2 行**：给出 token / 时间 / 结构三维对照。
3. **Threats**：需写明 EraRAG 实现在 CPU/Windows/大规模下的死锁风险（#9）。
4. **口径说明**：本实验为 V1 口径（`internal = num_nodes − len(leaf_nodes)`）；增量树结构差异为**首次观测**，建议后续以「同叶集下的树同构性」做更严格核验。
