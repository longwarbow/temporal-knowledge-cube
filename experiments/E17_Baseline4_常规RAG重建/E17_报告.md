# E17 报告 —— Baseline #4：常规实践基线「RAG + 定期全量重建」

> 2026-10-21 ｜ 回应投稿前检查表 **P0-11（Baseline 补强）**
> 定位：E14（EraRAG）是"最接近的已发表系统"；本实验补的是审稿人真正会问的朴素对照——
> **普通工程团队今天会怎么做**：分块 + 向量索引 + 夜间全量重建。
> 环境：Python 3.9（`.venv_e14`）｜ CPU-only ｜ MiniLM 384-d（与 E14 同一模型）｜ GLM-4-Flash（与 E14 同 key 同模型）｜ 同机同回次

## 1. 设计（不设陷阱）

把常规路径按**最有利于它**的方式实现，三方对照（同语料 PHEME 300 贴、同嵌入、同 LLM）：

| 变体 | 维护路径 | 撤回语义 |
|---|---|---|
| **naive**（常规部署） | 全量重嵌 + 重建索引；撤回排队等下一次夜间重建 | 下一重建周期才生效 |
| **history+**（给基线的最好情况） | 标记删除（零 token、即时）+ as-of 可查历史 | 即时 |
| **ours** | 立方体增量（unit update）+ 声明状态 + 血缘 | 即时，最小重算 |

诚实性：token 全部取自 API usage；嵌入 CPU 实测墙钟；语料按 snowflake 反解的真实时间排序；
靶标声明经探测确认"确实在被检索"（top-3 命中 2/8 查询）后才撤回——避免"撤回了但检索不到"的无效对照。

## 2. Q1 成本（n=300，每万文档归一）

| 路径 | 墙钟/10k 文档 | LLM token/10k | 嵌入向量/10k |
|---|---|---|---|
| naive 全量重建（同回次热缓存） | **32.2 s** | 0（嵌入本地） | 10,000（全量重嵌） |
| naive 首次建索引（冷） | 278–303 s | 0 | 10,000 |
| **ours 立方体增量** | **0.007 s** | 0 | 0 |

- 常规 RAG 的重建成本是**嵌入算力**而非 LLM token：每晚把全部 10,000 文档重新嵌入 ≈ 32 s（CPU）。
- 我们的增量是 **0.67 µs/文档**（0.0002 s/300），与 E16 的 1.53 µs/event 同一数量级——两条独立实现互相印证。
- 差距 **≈3–4 个数量级**，且随语料增长线性扩大（重建 ∝ N 全量 vs 增量 ∝ Δ）。

## 3. Q2 时效：撤回 → 下一重建周期之间的陈旧窗口

靶标：源帖声明 `498341675476217856`（Ferguson，label=false，"Unarmed teenager #MikeBrown was shot ten times…"），撤回前在 top-3 中命中 2/8 个探针查询。三档重建预算（新文档到达 10% / 1% / 0.1% 后才重建）结果**完全一致**：

| 变体 | 窗口内把已撤回声明送入上下文 | 窗口内把它当**支持证据引用** | 重建后 |
|---|---|---|---|
| naive | **2/8（25%）** | **1/8（12.5%）** | 全部干净 |
| history+ | 0/8 | 0/8 | — |
| ours | 0/8 | 0/8 | — |

- **条件化表述**：在撤回前本会检中该声明的 2 个查询里，naive **100% 继续服务**它。
- 预算档位只改变窗口时长（15 条 vs 1 条新文档），不改变逐查询行为——**每一次重建之间的窗口都在重复同样的陈旧服务**。
- 典型引文（naive，窗口内）：
  - 问"Is there any post contradicting the source claim?" → 答 "**No** [1], [2], or [3] provide any posts that contradict the source claim."（矛盾帖存在，只是那条支持证据已被撤下）
  - 问"Which posts dispute or refute the original claim?" → 答 "[2] The post by @larryelder **disputes or refutes the original claim**…"（引用的正是已撤回文档）

## 4. Q3 引用可溯性

"撤回后答案仍引用已撤回文档"这一失效形态**依赖引用可追溯**：
- 在带引用的朴素 RAG 中，它表现为窗口内的显式引用（如上，可实测、可计数）；
- 在不带引用轨迹的典型生产部署中，同样的事情发生但**不可验证**——因此"是否仍引用已撤回声明"不是 RAG 与我们的区别，**撤回传播延迟**（rebuild-period latency）才是。
- history+ 说明：给朴素 RAG 补上标记删除即可消除该窗口——**代价是把维护路径改成本实验的第二个变体**，即承认逐事件状态维护是必要的；而即便如此它仍无 as-of 语义之外的可合并度量与血缘。

## 5. 结论（供 §7.7 回写）

1. **成本**：常规"重建一切"基线的维护成本是嵌入算力（≈32 s/10k 文档，CPU），我们的增量路径低 3–4 个数量级（0.67 µs/文档，与 E16 独立印证）。
2. **时效**：在两个重建周期之间，已撤回声明在 100% 的"本会命中"查询里被继续服务，12.5% 的探针查询把它当支持证据引用；三档重建预算下行为一致。
3. **可溯性**：引用可追溯使失效可计数；无引用轨迹则同样失效但不可见——所以正确的问题是撤回传播延迟，而非引用。
4. **对 E14 的定位补强**：EraRAG 的失败是"增量路径本身坏"；E17 说明**即使增量路径不坏（history+），常规 RAG 也拿不出可合并度量与血缘**——两个基线从不同方向夹出 C3 的必要性。
